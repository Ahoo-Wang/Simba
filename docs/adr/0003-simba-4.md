# ADR 0003: Simba 4.0 Scope

- Status: Accepted
- Date: 2026-10-10

## Context

3.2 and 3.3 shipped the lease engine, the local lease guard, Redis release broadcasts and fencing tokens without
breaking the public API. A few rules that should hold could not be enforced compatibly. 4.0 is the window for
exactly those, and nothing speculative.

## Decision

1. **`MutexOwner` is a value.** A final `data class` that records the backend time it was observed at
   (`observedAt`) plus a local monotonic anchor, and derives `currentAt` from them. Subclassing to override the
   clock ends; `MutexOwnerEntity` and its mutable `version` / `currentDbAt` go away. `hasOwner()` and
   `isInTransition` collapse into one predicate.
2. **No user code under internal locks.** State transitions are computed under the lock; `onAcquired` /
   `onReleased` run outside it on the same sequential executor, preserving order. `stop()` waits for its release
   callback through that executor, or runs it inline when already on the callback thread.
3. **`simba-core` depends only on kotlin-logging.** Guava (`newSequentialExecutor`, `ThreadFactoryBuilder`,
   `@Immutable`) and cosid (process id, host address) are replaced with small JDK-based code. Contender id format
   stays `counter:pid@host`.
4. **Explicit backend selection.** `simba.backend=jdbc|redis|zookeeper`. Unset with a single backend module on the
   classpath behaves as before; unset with several fails fast instead of depending on auto-configuration order.
5. **Remove compatibility leftovers.** `MutexRetrievalServiceFactory` (no implementation), `AcquireResult.of(String)`,
   Redis per-contender channel subscriptions and legacy queue deletion (4.0 requires upgrading from 3.2+), and the
   `MutexOwnerRepository` methods the engine does not use (initialization moves to its own interface).
6. **JDBC fencing on by default** (ADR 0002): `simba.jdbc.fencing=true`.

### Not in 4.0

A JDBC dialect SPI: with MySQL as its only implementation it would be an abstraction for a guessed need. It is
added, additively in 4.x, together with a second dialect when one is actually supported.

## Upgrade guide (summary)

- Upgrade Redis deployments from 3.2 or later (rolling upgrades from 3.1 must pass through 3.2/3.3 first).
- JDBC: run `upgrade-simba-mysql-fencing-token.sql` on existing tables, or set `simba.jdbc.fencing=false`.
- Applications with more than one backend module must set `simba.backend`.
- Code that subclassed `MutexOwner`, used `MutexOwnerEntity`, `MutexRetrievalServiceFactory` or the removed
  repository methods must migrate to the value type and the narrowed interfaces.

## Consequences

- 3.3.x fixes are made on a maintenance branch cut from the `v3.3.0` tag while `main` carries breaking changes.
- Each item ships as its own PR with its tests and EN/ZH docs; 4.0.0 is released after a full review.
